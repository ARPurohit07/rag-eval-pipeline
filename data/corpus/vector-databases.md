# Vector Databases

A vector database is a data store optimized for indexing and querying high-dimensional embedding vectors by approximate similarity rather than exact match. Given a query vector, it returns the k stored vectors whose distance (commonly cosine distance, dot product, or Euclidean/L2 distance) to the query is smallest, using an index structure that avoids comparing the query against every stored vector — a brute-force scan that would otherwise cost O(n) per query.

The two dominant families of approximate nearest neighbor (ANN) indexes are graph-based and clustering/quantization-based. Graph-based indexes, most notably HNSW (Hierarchical Navigable Small World), build a multi-layer graph where each vector is a node connected to a small set of nearby neighbors; a query greedily walks the graph from an entry point toward closer and closer neighbors, giving very fast, high-recall search at the cost of higher memory usage and slower index build/insert times. Clustering-based indexes such as IVF (Inverted File Index) partition the vector space into clusters (via k-means) and, at query time, only search within the clusters closest to the query, trading some recall for lower memory and faster inserts; IVF is often combined with product quantization (IVFPQ) to compress vectors and shrink the index further.

pgvector is a PostgreSQL extension that adds a native `vector` column type plus distance operators (`<->` for L2, `<#>` for negative inner product, `<=>` for cosine distance) and index types (IVFFlat and HNSW) directly inside Postgres. Its main appeal is operational: teams that already run Postgres get vector search without introducing a separate database system, can join vector search results against relational metadata in a single SQL query, and get transactional guarantees and existing backup/replication tooling for free. The trade-off compared to purpose-built vector databases (Pinecone, Weaviate, Qdrant, Milvus) is typically raw scale and some advanced features (e.g., very large-scale sharded search, some quantization schemes), though pgvector has closed much of that gap as it has matured.

Every ANN index trades recall (the fraction of true nearest neighbors actually returned) for speed and memory. Recall is tunable: HNSW exposes parameters like `ef_search` (how many candidates to explore during a query) and `m` (how many graph edges per node), while IVF exposes `nprobe` (how many clusters to search). Increasing these parameters raises recall and latency together; a common evaluation practice is to plot a recall-vs-queries-per-second curve and choose an operating point that meets a latency budget while maximizing recall.

In a retrieval-augmented generation system, the vector database is typically just one half of the retrieval layer — filtering by exact metadata (document source, date range, permissions) is usually done as a SQL `WHERE` clause alongside or before the vector search, and the final ranking is often a fusion of this semantic search with a separate lexical search such as BM25.
