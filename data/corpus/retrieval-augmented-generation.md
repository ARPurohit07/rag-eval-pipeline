# Retrieval-Augmented Generation (RAG)

Retrieval-Augmented Generation is an architecture that couples a language model with an external retrieval step: instead of relying solely on knowledge baked into the model's parameters during pretraining, the system first retrieves relevant passages from an external corpus and then conditions the model's generation on those retrieved passages, typically by inserting them into the prompt. The term was coined in a 2020 paper by Lewis et al., though the general idea of grounding generation in retrieved evidence predates that specific formulation.

RAG addresses three well-known weaknesses of relying on a language model's parametric knowledge alone. First, hallucination: a model asked about facts it never saw, or saw rarely, during training will often generate plausible-sounding but incorrect text rather than admitting uncertainty; grounding generation in retrieved source text gives the model something concrete to draw from and gives users a way to verify claims against a cited source. Second, staleness: a model's knowledge is frozen at its training cutoff, while a retrieval corpus can be updated continuously without retraining the model. Third, cost and specificity: fine-tuning a large model to memorize a narrow, proprietary, or frequently-changing document set is expensive and often unnecessary if the same documents can simply be retrieved at query time.

A typical RAG pipeline has an offline (indexing) path and an online (query) path. Offline, documents are split into chunks, each chunk is embedded, and the embeddings (plus the chunk text and metadata) are stored in a vector index. Online, an incoming query is embedded with the same model, the vector index returns the top-k most similar chunks, and those chunks are formatted into a prompt template along with the user's question and handed to the generator LLM, which produces an answer conditioned on that context.

The quality of a RAG system is bottlenecked by whichever stage performs worst: if retrieval fails to surface the passage that actually contains the answer, no amount of generation quality can recover, because the model was never given the right information. This is why RAG evaluation typically decomposes into retrieval metrics (did we find the right passages?) and generation metrics (given the passages we found, did the model produce a faithful, relevant answer?) rather than only scoring the final answer end-to-end.

Common failure modes include: retrieving passages that are topically related but do not actually answer the question (leading to a plausible but wrong answer); retrieving the right passage but having the generator ignore it in favor of its own parametric knowledge; retrieving too many or too few chunks, either diluting the context with irrelevant text or omitting necessary information; and the generator "hallucinating" a synthesis that goes beyond what the retrieved context actually supports, which is why faithfulness (does the answer only make claims supported by the retrieved context?) is tracked as a distinct metric from correctness. More advanced variants extend the basic pattern: query rewriting or decomposition before retrieval, iterative or multi-hop retrieval where the model retrieves, reasons, and retrieves again, and re-ranking retrieved candidates with a more expensive cross-encoder model before generation.
