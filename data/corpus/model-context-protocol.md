# Model Context Protocol (MCP)

The Model Context Protocol (MCP) is an open standard for connecting AI applications to external tools, data sources, and systems through a common client-server interface, rather than every AI application and every external system needing a bespoke, one-off integration. Before a shared protocol, connecting an LLM application to N different tools or data sources typically required writing N different custom integrations; MCP aims to turn this into an M-times-N problem into an M-plus-N problem, where any MCP-compatible client can talk to any MCP-compatible server without custom glue code for each pair.

An MCP server exposes some combination of three primitives. Tools are callable functions with a defined input schema that the AI model can invoke to take an action or fetch information (for example, running a database query, sending a message, or searching the web) — conceptually similar to function calling/tool use already supported by most LLM providers, but standardized so the same tool server works across different client applications. Resources are addressable pieces of data (files, database records, API responses) that a client can read and provide as context to the model, distinct from tools in that reading a resource is meant to be a side-effect-free retrieval rather than an action. Prompts are reusable, parameterized prompt templates that a server can expose so that common interaction patterns don't need to be re-authored in every client that wants to use that server.

Communication between an MCP client and server happens over a small set of transport options — commonly standard input/output (stdio) for a server running as a local subprocess on the same machine, or HTTP (including support for streaming responses) for a server running remotely — with messages exchanged as JSON-RPC, a lightweight remote-procedure-call format built on JSON. Regardless of transport, the interaction pattern is the same: a client discovers what tools/resources/prompts a server offers (via a listing call), and then invokes specific tools or reads specific resources by name with structured arguments, receiving structured results back.

A practical benefit of standardizing this interface is composability: a single MCP server implementation for, say, a company's internal ticketing system, or a database, or a version control host, can be written once and then used by any MCP-compatible AI application — a chat assistant, an IDE integration, an autonomous agent — without that server needing to know anything about which specific application is calling it. This mirrors the earlier value proposition of the Language Server Protocol (LSP) in code editors, which let one language server (say, for Python) work with any LSP-compatible editor, instead of every editor needing its own bespoke Python language support.

Security and scoping are active design concerns for MCP deployments: because a tool call from an MCP server can have real side effects (sending data externally, modifying files, making purchases), clients and users need visibility into what a given server's tools can actually do, ideally with per-tool or per-action permissioning, and should be cautious connecting to untrusted MCP servers in the same way one would be cautious installing an untrusted browser extension or granting an untrusted app broad account access.
