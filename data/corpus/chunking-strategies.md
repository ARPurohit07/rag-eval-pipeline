# Chunking Strategies for Retrieval

Chunking is the process of splitting source documents into smaller passages before embedding and indexing them, and it is one of the most under-appreciated levers in a RAG system's quality — even a perfect retriever and a perfect generator cannot produce a good answer if the relevant information was split across chunk boundaries in a way that neither chunk alone contains it.

Fixed-size chunking splits text every N tokens (or characters), optionally with an overlap between consecutive chunks so that content near a boundary still appears whole in at least one chunk. It is simple and predictable, and overlap (commonly 10-20% of the chunk size) directly mitigates the boundary problem, but fixed-size splitting is agnostic to the document's actual structure and can still cut a sentence or a table row in half.

Recursive character/token splitting improves on naive fixed-size splitting by trying a prioritized list of separators — paragraph breaks, then sentence breaks, then word breaks — recursively falling back to a smaller separator only when a chunk is still too large after splitting on a bigger one. This keeps chunks close to a target size while preferring to break at natural boundaries (like paragraph ends) rather than mid-sentence.

Semantic chunking uses embedding similarity to decide where to split: consecutive sentences are embedded, and a split point is inserted wherever the similarity between adjacent sentences drops sharply, on the theory that a sharp drop signals a topic change. Document-structure-aware chunking instead uses explicit structure already present in the source — markdown headers, HTML tags, PDF layout, or code function/class boundaries — to split along logical units the author already defined, which tends to produce the most coherent chunks when that structure is reliably present.

Chunk size itself is a trade-off along two axes. Larger chunks give the generator more surrounding context per retrieved chunk (fewer chances that a fact's necessary context got separated from the fact), but dilute the embedding: a long chunk covering several sub-topics gets one averaged embedding that may not closely match a query about any single sub-topic, hurting retrieval precision. Smaller chunks embed more precisely (an embedding of a focused, single-topic passage matches a focused query more closely) but risk fragmenting information that spans multiple sentences and increase the total number of vectors to index and search. A common mitigation is to embed and search over small chunks for precision, but expand each retrieved chunk to include its surrounding sentences or parent section before handing it to the generator, decoupling the unit of retrieval from the unit of context.
