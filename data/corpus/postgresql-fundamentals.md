# PostgreSQL Fundamentals Relevant to Search Systems

PostgreSQL is an open-source, object-relational database management system known for standards compliance, strong transactional guarantees (full ACID compliance), and an extension system that lets it take on capabilities well beyond a traditional row-store relational database, including full-text search, JSON document storage, geospatial data (via PostGIS), and, via pgvector, vector similarity search.

At the storage level, Postgres organizes data as rows within pages (typically 8KB blocks) within table files, and Postgres uses Multi-Version Concurrency Control (MVCC) to let readers and writers operate concurrently without blocking each other: rather than locking a row for the duration of a transaction, an update creates a new version of the row and marks the old version as no longer current for future transactions, while transactions already in progress continue to see the row version that was current when they started. This is why long-running transactions and un-vacuumed dead row versions ("bloat") are an operational concern — periodic vacuuming reclaims space from row versions no longer visible to any active transaction.

Indexing is central to query performance. A B-tree index (the default) is well suited to equality and range queries on ordered data and is what backs most primary keys and foreign keys. A GIN (Generalized Inverted Index) index is suited to data where a single column value contains multiple searchable elements — an array, a JSONB document, or the lexemes produced by full-text search — because it indexes each element separately and maps it back to the rows containing it, which is why Postgres's built-in full-text search (`tsvector`/`tsquery`) is typically backed by a GIN index. pgvector's HNSW and IVFFlat index types plug into this same general indexing framework, letting an approximate-nearest-neighbor vector index coexist with ordinary B-tree and GIN indexes on other columns of the same table.

A practical consequence of running vector search inside Postgres rather than a separate vector database is that a single SQL query can combine an ANN vector search with ordinary relational filtering and joins — for example, "find the 10 most semantically similar chunks to this query embedding, but only among documents owned by this user and tagged as published" — expressed as one query with a `WHERE` clause and an `ORDER BY embedding <=> query_vector LIMIT 10`, rather than requiring an application to query a vector database and a relational database separately and merge the results in application code. The trade-off is that the vector index shares the same server's resources (memory, CPU, I/O) with the rest of the application's relational workload, so a very large or very high-throughput vector search workload can be a reason to consider a dedicated vector database instead.

Connection handling matters for any application issuing many short-lived queries, including a retrieval service: opening a new physical Postgres connection is relatively expensive (it forks a new backend process per connection), so production systems typically use a connection pooler (such as PgBouncer, or a pool built into the application's database driver) to reuse a smaller number of physical connections across many logical client requests, rather than opening and closing a connection per query.
